# 手机端不留全库正文（Lite 的边界）

本应用**不在手机上保留全库正文的副本**。因此以下四件事在本版不存在：搜正文、删除笔记前报「有几篇链到这里」、改名时报「会断多少条」、标签可点、`tasks` 查询块执行。

这不是省事，是这条路走不通。**任何一份存在手机上的正文副本，都只能是快照**，而快照有两个说不出口的问题：

1. **可能不全** —— 一次全量备库实测 4.7 分钟（877 篇、零 403，见 [#38 的实测成绩单](https://github.com/d1cky1990/GitObsidianLite/issues/38#issuecomment-6250316416)）。手机上它常常跑不完：标签页挂后台会被系统冻结、用户不盯着看。于是「功能只在备齐了的人那里存在」。
2. **可能是旧的** —— 就算备齐了，PC 上改了措辞、删了句子，手机上仍拿旧正文去匹配。界面能交代「只覆盖了多少篇」，**交代不了「你看的是什么时候的内容」**，而后者比前者更容易骗人。

第二种问题补不上，因为**刷新不了**：仓库平台没有搜索端点（Gitee 完全没有；GitHub 有但仅默认分支、单文件 < 384 KB、10 次/分钟，且两家行为不一致会让搜索体验随供应商变形，[#17](https://github.com/d1cky1990/GitObsidianLite/issues/17#issuecomment-5947644914) 已否决「按供应商换搜索」）。要在服务端算，就得每次把全库重取一遍——而平台免费档**一次请求最多只能往外发 50 个请求、6 条并发**，八百多篇要十几批，查询会以分钟计；把结果存下来就是服务端有了状态，那是另一套工程。

一句话：**Lite 不上手机留全库正文，所以「需要全库正文才能回答的问题」，一个都不答。**

## Considered Options

- **默认关、只给搜索用的副本**（[#32](https://github.com/d1cky1990/GitObsidianLite/issues/32#issuecomment-5935944523) 定的形态，[#33](https://github.com/d1cky1990/GitObsidianLite/issues/33#issuecomment-5949983801) 已实现）—— 否决并拆除。它就是快照，两个问题都在。覆盖范围那句话能说，内容新旧那句话不能说。
- **升格成手机上的笔记镜像**（默认开、争取备全、打开笔记就地读）—— 否决。除了同样的快照问题，还撞两条既定的线：「本地正文只给搜索用、不兼作正文来源」，以及「切编辑前先核一次远端改动」（就地读会让「我手上这份是不是最新的」改由副本判断，等于重写冲突判定）。且「镜像」这个承诺在手机上守不住——iOS 的 Safari 对**七天没用过的站点**会清掉本地存储（加到主屏幕的网页除外），而「手机低频查看」正是被这条规则挑中的用法。
- **服务端缓存一份正文**（键值存储）—— 否决。破「服务端不存状态」。为一句提示语养一套过期、失效、备份的机制，与本项目其余部分的简单性不成比例。
- **用 GitHub 自带的代码搜索** —— 否决。见上：范围与限额都不够，且会让「同一份部署换个供应商，搜索体验就换一个」。

## Consequences

- **搜索只到标题与路径**，靠手机上已有的那份全库名单，零新增请求，**永远是新的**。界面上标一句「只搜标题与路径」，不解释原因。
- 四件依赖全库正文的事一并**不做**（[#43](https://github.com/d1cky1990/GitObsidianLite/issues/43) 的结论）。翻案条件是任一条成立：托管平台能存状态、仓库平台真出了可用的搜索端点、或者需求方自己用着觉得缺。**这三条都不成立时，不要再论证一遍。**

- **恢复的代价要认**：拆掉的不只是开关，是「存哪、多大、什么时候刷新、未就绪怎么说话」那一整套规则、两个模块与它们的测试、服务端一条批量取正文的接口。将来要捡回来，得从头再定一遍。

- **拆的时候别误伤**：那次实现顺带修掉的两个缺陷是独立的——库内图片永远停在「正在确认位置」的占位、断网时打开的那页恢复联网后名单不自愈。它们与正文副本无关，不跟着拆。
